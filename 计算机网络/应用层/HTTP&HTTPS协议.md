# HTTP & HTTPS 知识笔记

**（从原理理解到工程排障的一体化视角）**

------

## 一、HTTP / HTTPS 在网络体系中的位置

### 1. 协议分层视角

- **HTTP / HTTPS 属于应用层协议**
- 它们并不负责“数据如何到达”，而只关心：
  - 请求的语义（我要做什么）
  - 响应的语义（结果是什么）

依赖关系如下：

```
HTTP
HTTPS = HTTP + TLS
TLS 依赖 TCP
TCP 依赖 IP
```

👉 **结论**：
 HTTP/HTTPS 是否能工作，前提是 **DNS → IP → TCP** 全部正常。

------

## 二、从浏览器输入理解 HTTP 的完整生命周期

### 1. DNS 解析阶段（是否“找得到服务器”）

- 浏览器解析 URL 中的域名
- 查询顺序：
  1. 本地缓存 / 操作系统 DNS
  2. 网络 DNS 服务器
- 目标：**将域名解析为 IP**

> 若 DNS 失败，HTTP 尚未开始。

------

### 2. TCP 建立阶段（是否“能连上服务器”）

- 浏览器与服务器通过 **TCP 三次握手**建立连接
- HTTP 默认端口：80
- HTTPS 默认端口：443

👉 这一阶段关注的是：

- 网络是否可达
- 防火墙 / 安全组 / 端口监听是否正确

------

### 3. HTTP 请求发送阶段（应用层开始工作）

#### HTTP 请求结构

```
请求行
请求头
空行
请求体（可选）
```

##### 请求行（Request Line）

- 请求方法（GET / POST / PUT / DELETE …）
- 资源路径（URL Path）
- 协议版本（HTTP/1.1 / HTTP/2）

##### 请求头（Headers）

请求头的本质作用：**让服务器“正确理解请求上下文”**

核心关注点包括：

- `Host`：请求访问的域名（虚拟主机必需）
- `Accept`：客户端期望的数据类型
- `User-Agent`：客户端系统 / 浏览器信息
- `Authorization` / `Cookie`：身份与会话信息
- `Connection`：连接管理策略

------

### 4. HTTP 响应与状态码的工程意义

#### HTTP 响应结构

```
状态行
响应头
空行
响应体
```

#### 状态码的真正作用

HTTP 状态码不仅表示“成功或失败”，而是用于 **精确表达请求处理结果的责任归属**：

- **2xx**：请求成功，服务器正确处理
- **4xx**：客户端请求存在问题
- **5xx**：服务器处理请求时发生异常

👉 在排障中：

+ **4xx 优先查客户端请求**

+ **5xx 优先查服务器日志**

------

## 三、HTTP 的核心局限性（HTTPS 的出现背景）

如果使用明文 HTTP，会存在三类根本性风险：

1. **窃听风险**：通信内容可被第三方获取
2. **篡改风险**：数据在传输过程中被修改
3. **冒充风险**：无法确认通信对方的真实身份

👉 HTTP 无法解决：

- 数据机密性
- 数据完整性
- 身份可信性

------

## 四、HTTPS 的本质：HTTP + TLS

### 1. HTTPS 解决了什么问题？

HTTPS 通过 TLS 提供三大安全特性：

| 安全目标 | 实现方式             |
| -------- | -------------------- |
| 加密性   | 对称加密（会话数据） |
| 完整性   | 摘要 / 校验机制      |
| 身份认证 | 数字证书 + CA        |

------

### 2. 对称加密 vs 非对称加密（工程视角）

- **非对称加密**
  - 用于：身份认证、密钥交换
  - 特点：安全但计算成本高
- **对称加密**
  - 用于：正式通信数据加密
  - 特点：高效，适合大规模数据传输

👉 HTTPS 的设计原则：
 **“非对称解决信任，对称解决性能”**

------

## 五、TLS 握手与数字证书的真实工作方式

### 1. 数字证书的角色

- 证书由 **CA 签发**
- 包含：
  - 服务器域名
  - 服务器公钥
  - 有效期
  - CA 的数字签名

👉 CA **不保管服务器证书**，而是：

- 用 CA 私钥对证书签名
- 浏览器用 CA 公钥验证签名

------

### 2. 浏览器验证证书时做什么？

浏览器会检查：

1. 证书域名是否与访问域名一致
2. 证书是否在有效期内
3. 是否由受信任 CA 签发
4. 证书链是否完整
5. 签名是否可被验证

任一失败 → TLS 连接终止 → 提示“连接不安全”

------

### 3. HTTPS 为什么“看起来慢”但实际上可接受？

主要耗时点：

- TLS 握手
- 证书验证
- 密钥协商

现代 Web 中可忽略的原因：

- 网络设备性能提升
- 计算性能提升
- 浏览器内置根证书
- 会话复用（Keep-Alive / TLS Session）

------

## 六、HTTP & HTTPS 的工程级排障模型（核心能力）

这是你在学习中形成的 **最重要成果**。

### HTTPS 网站访问问题排查流程（标准 SOP）

#### 第一层：DNS & 网络连通

- 域名是否可解析
- 是否能 ping 通服务器

👉 判断是否“能找到并到达服务器”

------

#### 第二层：TCP & 端口

- 80 / 443 是否放行
- 防火墙 / 安全组
- 服务是否监听端口

👉 判断是否“能建立连接”

------

#### 第三层：TLS / 证书

- 证书域名
- 有效期
- CA 信任
- 证书链完整性

👉 判断是否“能建立安全通道”

------

#### 第四层：HTTP 语义

- 请求方法是否正确
- URL 是否匹配 API
- 是否携带必要参数 / 鉴权
- 结合状态码定位责任方

👉 判断是否“正确处理业务请求”
