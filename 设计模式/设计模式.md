# 设计模式

## 设计原则

- 找出应用中需要变化之处，把它们独立出来，不要和那些不需要变化的代码混在一起。
- 针对接口编程，而不是针对实现编程。这里的接口确切的说是一种“超类型（ supertype ）”，具体来说就是在编程时将变量的声明类型定义为一个抽象类或一个接口，只要是具体实现此超类型的类所产生的对象都可以指定给变量，这使得在声明类时不用考虑执行时的真正类型。
- 多用组合（“ has-a ”），少用继承（“ is-a ”）。
- 为了交互对象之间的松耦合设计而努力。
- 开放-关闭原则（开闭原则）：类应该对扩展开放，对修改关闭。
- 依赖倒置原则：要依赖抽象，不要依赖具体类。为了实现这个原则，可以尽量遵循：变量不可以持有具体类的引用；不要让类派生自具体类；不要覆盖基类中已经实现的方法。
- “最少知识”原则（迪米特法则）：一个对象应当尽可能少地了解其他对象的内部细节，只与直接朋友通信。直接朋友包括：当前对象自身（ `this` ）、成员变量、方法参数、方法内部创建的对象。如不应该使用`customer.getAddress().getCity().getName()` ，而是 `customer.getCityName()` ，由 `Customer` 内部处理细节。
- 好莱坞原则：别调用我们，我们会调用你。低层模块不要主动控制流程，高层框架（模块）负责整体流程控制，并在合适的时候回调低层模块的代码。这样可以避免程序控制流程复杂（如低层依赖高层、高层依赖另一个低层，模块依赖之间出现环状）。
- 单一职责原则：一个类应该只有一个引起变化的原因。



### SOLID 原则

- 单一职责原则（ Single Responsibility Principle ）：一个类只负责一件事，只有一个引起它变化的原因。
- 开闭原则（ Open-Closed Principle ）：对扩展开放，对修改关闭。新增加功能尽量通过扩展实现，而不是修改已有代码。
- 里氏替换原则（ Liskov Substitution Principle ）：子类应该能替换父类，并且不影响程序正确性。
- 接口隔离原则（ Interface Segregation Principle ）：不要强迫类依赖它不需要的方法；多个小接口优于一个大接口。
- 依赖倒置原则（ Dependency Inversion Principle ）：高层模块不依赖低层模块，二者都依赖抽象（接口）。

速记：

- S ：一个类只做一件事。
- O ：新增功能别改旧代码。
- L ：子类必须能当父类用。
- I  ：接口必须小而专一。
- D ：依赖接口，不依赖实现。



## 创建型设计模式

创建型设计模式抽象了实例化过程。它们帮助一个系统独立于如何创建、组合和表示它的那些对象。

- 一个类创建型模式使用继承改变被实例化的类
- 一个对象创建模式将实例化委托给另一个对象



### Abstract Factory （抽象工厂）——对象创建型模式

**意图**

提供一个接口以创建一系列相关或相互依赖的对象，而无须指定它们具体的类。

**适用性**

- 一个系统要独立于它的产品的创建、组合和表示
- 一个系统要由多个产品系列中的一个来配置
- 要强调一系列相关的产品对象的设计以便进行联合使用
- 提供一个产品类库，但只想显示它们的接口而不是实现

**参与者**

- AbstractFactory ：声明一个创建抽象产品对象的操作接口
- ConcreteFactory ：实现创建具体产品对象的操作
- AbstractProduct ：为一类产品对象声明一个接口
- ConcreteProduct ：定义一个将被相应的具体工厂创建的产品对象；实现 AbstractProduct 接口
- Client ：仅使用由 AbstractFactory 和 AbstractProduct 类声明的接口

AbstractFactory 将产品对象的创建延迟到它的 ConcreteFactory 子类。



#### 例子

##### 背景

某电子产品由两种配件组成：电池和屏幕。当前供应链市场中提供的电池型号有2种：大容量电池、小容量电池， 提供的屏幕型号有3种：高清、超清、4K。该电子产品的生产厂家目前有3条产品线：低端产品线（小容量电池+高清屏幕）、中端产品线（大容量电池+超清屏幕）、高端产品线（大容量电池+4K屏幕）。未来产品的配件可能出现更多的型号，厂家可能增加其他的产品线或修改已有产品线（更换产品配件类型）。请为该厂家编写一个接口，用于生产客户需要的电子产品。



##### 面向实现编程

分析：由需求可知应该包括以下几个类：工厂类（厂家）、产品类（电子产品）、电池类、屏幕类，其中电池类与屏幕类的对象作为产品类的属性。

思路：

1. 分别定义一个电池类和一个屏幕类；
2. 定义一个产品类，它有两个对象属性：电源对象、屏幕对象；
3. 定义一个工厂类，包括一个创建配件对象的方法。
4. 将配件对象交给产品类组装。

电池类：

```java
public class Battery {
    String type;

    public Battery(String type){
        this.type = type;
    }

    public String getType() {
        return type;
    }
}
```

屏幕类：

```java
public class Screen {
    String type;

    public String getType() {
        return type;
    }

    public Screen(String type){
        this.type = type;
    }
}
```

产品类：

```java
public class Product {
    String type;

    Battery battery;
    Screen screen;

    public Product(Battery battery, Screen screen) {
        this.battery = battery;
        this.screen = screen;
    }

    public void printProduct() {
        System.out.println("This product is " + type + ".Its battery is "
                + battery.getType() + ".Its screen is " + screen.getType());
    }
}
```

工厂类：

```java
public class ProductFactory {
    
    public Product createProduct(String type) {
        if (type.equalsIgnoreCase("low")) {
            Battery battery = new Battery("small capacity");
            Screen screen = new Screen("high definition");
            return new Product(battery, screen);
        } else if (type.equalsIgnoreCase("middle")) {
            Battery battery = new Battery("big capacity");
            Screen screen = new Screen("ultra definition");
            return new Product(battery, screen);
        } else if (type.equalsIgnoreCase("high")) {
            Battery battery = new Battery("big capacity");
            Screen screen = new Screen("4K definition");
            return new Product(battery, screen);
        }
        return null;
    }
}
```

客户类：

```java
public class Client {
    public static void main(String[] args) {
        ProductFactory factory = new ProductFactory();

        factory.createProduct("low").printProduct();
        factory.createProduct("middle").printProduct();
        factory.createProduct("high").printProduct();
    }
}
```

上面代码存在的问题：

1. 电池类、屏幕类，甚至产品类在设计时是直接面向实现进行编程，没有考虑继承。当电池、屏幕等配件有新的型号时，并不能很好的区分（代码中使用的是 `type` 字段），而且不同的配件可能有各自的属性，所以电池类、屏幕类应该考虑使用继承。同样的产品类也建议使用继承的方式编写，因为从现实思考：低端产品、中端产品、高端产品应该是不同的类型的产品，它们是产品的子类。将它们通过继承改写，可以增加扩展性：当要新增配件类型与产品时很有效。
2. 工厂类与产品类、配件类对象的实例化高度耦合，不利于修改。工厂类只提供了一个接口去实例化对象，在这个接口中同时实例化了电池类对象、屏幕类对象、产品类对象，且还通过对参数条件判断来生产不同的产品，增加了代码复杂度。当要新增加一个产品线或修改已有产品线（如大容量电池+高清屏幕），则必须修改已有工厂类的方法，带来修改的困难与维护的不方便。所以应该将工厂类抽象出来，并且将对象实例化的部分进行细粒度处理——提供不同的接口去实例化不同的配件类对象。
3. 产品是配件的组装，产品的类型是由配件决定，所以工厂类应该只产生组成产品的配件，即工厂实例化产品依赖的一系列对象，工厂并不直接生产产品。
4. 对于一个产品，它所需要的配件应该由它所在的生产线（工厂）决定，这样可以使得当产品定位不变时，只修改生产线就能完成产品生产。



##### 面向接口编程&抽象工厂

通过分析，需要做如下修改：

1. 将产品类、电池类、屏幕类做为基类，分别派生出各自的子类：低端产品类、中端产品类，高端产品类，大容量电池类、小容量电池类、高清屏幕类、超清屏幕类、4K屏幕类，具体产品子类中有对电池类、屏幕类对象的引用。
2. 将工厂类抽象出一个抽象工厂类，抽象工厂类对外提供创建电池类对象、屏幕类对象的接口，接口由其子类实现。
3. 根据产品线定义不同的工厂类继承自抽象工厂类，并实现创建电池对象、屏幕对象的接口。
4. 具体产品子类的构造方法接受一个抽象工厂类型的参数，通过该参数获得产品需要的配件。
5. 客户类中有变量是抽象工厂类型，它是一个具体工厂类对象的引用，通过该变量产生对应的具体产品。

分析：修改后的程序虽然类变得更多，但都是对一些基类或接口继承产生的子类。程序结构变得复杂，却可以使程序更易维护与扩展：

1. 通过继承，当有新的产品或配件出现时，可以不对已有代码进行修改，新增加类即可。
2. 通过抽象工厂，客户并不需要知道具体的工厂就可以生产产品，因为客户持有的是抽象工厂类型的变量，决定产品具体类型的是该变量对应的引用。
3. 抽象工厂提供是一组创建对象的接口，创建的对象正是产品对象的属性变量，以这种方式完成：**创建一系列相关或相互依赖的对象，而无须指定它们具体的类**。
4. 大量面向接口（广义接口，包括超类型、抽象类）编程，保证程序的“开-闭原则”。



##### 总结

**抽象工厂模式**——提供一个接口，用于创建相关或依赖对象的家庭，而不需要明确指定具体类。 

在例子中产品（电子产品）是由更小的产品（配件：电池、屏幕）组成，不同的配件组成决定了产品的市场定位，而抽象抽象工厂就负责创建与产品相关的配件（实际上对象的创建延迟到了具体工厂子类中）。





### Builder （生成器）——对象创建型模式

**意图**

将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

**适用性**

- 当创建复杂对象的算法应该独立于该对象的组成部分以及它们的装配方式时
- 当构造过程必须允许被构造的对象有不同的表示时

**参与者**

- Builder ：为创建一个 Product 对象的各个部件抽象接口
- ConcreteBuilder ：实现 Builder 的接口以构造和装配该产品的各个部件；定义并跟踪它所创建的表示；提供一个检索产品的接口
- Director ：构造一个使用 Builder 接口的对象
- Product ：表示被构造的复杂对象，ConcreteBuilder 创建该产品的内部表示并定义它的装配过程；包含定义组成部件和类，包括将这些部件装配成最终产品的接口



### Factory Method （工厂方法）——对象创建型模式

**意图**

定义一个用于创建对象的接口，让子类决定实例化哪一个类。 Factory Method 使一个类的实例化延迟到其子类。

**适用性**

- 当一个类不知道它所必须创建的对象的类的时候
- 当一个类希望由它的子类来指定它所创建的对象的时候
- 当类将创建对象的职责委托给多个帮助子类中的某一个，并且你希望将哪一个帮助子类代理者这一信息局部化的时候

**参与者**

- Product ：定义工厂方法所创建的对象的接口
- ConcreteProduct ：实现 Product 接口
- Creator ：声明工厂方法，该方法返回一个 Product 类型的对象。Creator 也可以定义一个工厂方法的缺省实现，它返回一个缺省的 ConcreteProduct 对象；可以调用工厂方法以创建一个 Product 对象
- ConcreteCreator ：重定义工厂方法返回一个 ConcreteProducr 实例



#### 例子

##### 背景

某服装商店正在销售自有的服装，如衬衫、外套、牛仔裤、……请为该商店设计一个服装订购功能，传入服装的类型，返回相应的服装对象。该商店在未来打算分成三个专营商店：男士服装、女士服装、儿童服装，不同的年龄的同类服装有所差异，如男士衬衫与女士衬衫在版型上不同。



##### 面向实现编程

思路：

1. 直接在方法内部，根据参数进行对象的实例化。

服装商店类：

```java
public class ClothesShop {

    public Clothes orderClothes(String type) {
        Clothes clothes;

        if (type.equalsIgnoreCase("shirt")) {
            clothes = new Shirt();
        } else if (type.equalsIgnoreCase("coat")) {
            clothes = new Coat();
        } else if (type.equalsIgnoreCase("jeans")) {
            clothes = new Jeans();
        } else {
            return null;
        }

        return clothes;
    }
}
```

服装基类：

```java
public class Clothes {

    String type;
    double price;

    public void printInfo() {
        System.out.println("服装类型："+type+"，价格："+price);
    }
}
```

衬衫类：

```java
public class Shirt extends Clothes {

    public Shirt() {
        this.type = "shirt";
        this.price = 119.9;
    }
}
```

外套类：

```java
public class Coat extends Clothes{

    public Coat(){
        this.type = "coat";
        this.price = 188.8;
    }
}
```

牛仔裤类：

```java
public class Jeans extends Clothes{

    public Jeans(){
        this.type = "jeans";
        this.price = 78.6;
    }
}
```

在上面的代码中，对服装类对象的实例化是在订购方法中显式调用服装类的构造方法实现的，这是面向对象语言中最基本、也是初学者普遍使用的对象实例化方法，即在需要对象的地方直接通过 `new` 实例化对象。这样的做法存在以下几个问题：

1. 在程序代码中会随处看到大量且随意的 `new` 关键字及构造方法，如果构造方法的参数被修改，那么对原有代码的修改将会“牵一发而动全身”，不利于代码的维护与修改。
2. 如果新增一个或多个方法都需要实例化对象，那么就要在每个方法中都写同样的实例化代码，则这段代码是大量重复的，没有考虑到代码的复用，和上一条相似地它也会引起“牵一发而动全身”的修改。



##### 代码封装——简单工厂方式

为了解决上面存在的问题，最好的方式就是采用**简单工厂**的编程习惯（它严格来说并不是设计模式）。

思路：

1. 将对象实例化的代码从原代码处（可以看作是客户，如 `orderClothes` 方法）抽离出来封装在一个“工厂类”中。
2. 当客户需要实例化对象时，则调用工厂类提供的接口（方法）创建对象，即将对象实例化的任务交给工厂类来完成。

所以在上面的代码中只需要修改服装商店类和新增一个简单服装工厂类即可。

服装商店类：

```java
public class ClothesShop {

    public Clothes orderClothes(String type) {
        Clothes clothes = SimpleClothesFactory.createClothes(type);
        return clothes;
    }
}
```

简单服装工厂类：

```java
public class SimpleClothesFactory {

    public static Clothes createClothes(String type) {
        if (type.equalsIgnoreCase("shirt")) {
            return new Shirt();
        } else if (type.equalsIgnoreCase("coat")) {
            return new Coat();
        } else if (type.equalsIgnoreCase("jeans")) {
            return new Jeans();
        }
        return null;
    }
}
```

显然地，通过简单工厂的方式可以使得代码更有可维护性且更简洁，同时对于客户（如服装商店类的 `orderClothes` 方法）来说，它可以不必知晓对象创建的具体过程和类型（它只关心对象是不是 `Clothes` 类）。

简单工厂方法并不是设计模式的一种，它只是一种编程习惯——封装的思想，将程序中重复的代码进行了封装与重用。

在上面的实现中，我们将实例化对象的创建方法（ `createClothes` ）在简单工厂类中声明为静态（ `static` ）方法，这可以不用实例化简单工厂类的对象而直接调用创建方法，但存在的缺点是不能通过继承来改变创建方法的行为。

依然存在的问题：上面的代码解决了订购功能中实例化服装对象的需求，但是没有考虑到未来服装商店经营模式的改变——同样是订购外套，在男士商店与女士商店中订购的一定是版型、材质等不同的两件外套。



##### 由具体的类决定创建（实例化）的对象

考虑到服装商店未来的经营方式，顾客订购的服装是由他所在的商店决定的，比如他在男士商店订购衬衫，那么他最后得到的一定是男士衬衫，而不可能是女士衬衫。

思路：

1. 在服装商店类中定义一个创建方法（接口）用于实例化（创建）服装对象，其中基类中定义的是一个抽象方法，具体的实现（对象实例化）由子类完成。
2. 修改服装商店类的服装订购功能，改为通过新定义的创建方法来获取服装对象
3. 相应的产生九个服装类：男士（衬衫、外套、牛仔裤）、女士（衬衫、外套、牛仔裤）、儿童（衬衫、外套、牛仔裤），它们可以直接或间接继承自服装类。
4. 新产生三个服装商店类：男士服装商店类、女士服装商店类、儿童服装商店类，它们都是服装商店类的子类，实现基类中的创建方法（实例化对象）。

由于服装商店类与服装类数量过多，这里以男士服装商店类与男士衬衫类为例。

服装商店类：

```java
public abstract class ClothesShop {

    public Clothes orderClothes(String type) {
        Clothes clothes = createClothes(type);
        return clothes;
    }

    abstract Clothes createClothes(String type);
}
```

男士衬衫类：

```java
public class MaleShirt extends Clothes{

    public MaleShirt(){
        this.type = "male shirt";
        this.price = 99.8;
    }
}
```

男士服装商店类：
```java
public class MaleClothesShop extends ClothesShop {
    @Override
    Clothes createClothes(String type) {
        if (type.equalsIgnoreCase("shirt")) {
            return new MaleShirt();
        } else if (type.equalsIgnoreCase("coat")) {
            return new MaleCoat();
        } else if (type.equalsIgnoreCase("jeans")) {
            return new MaleJeans();
        }
        return null;
    }
}
```

测试类：

```java
public class Main {
    public static void main(String[] args) {
        ClothesShop shop = new MaleClothesShop();

        shop.orderClothes("shirt").printInfo();
        shop.orderClothes("coat").printInfo();
        shop.orderClothes("jeans").printInfo();
    }
}
```

上面的代码中，我们实现一个工厂方法设计模式——将原本应该在父类（ `ClothesShop` ）中进行的对象（ `Clothes` 类的对象）实例化延迟到了子类（ `MaleClothesShop` ）中，由子类的类型“决定”实例化对象的类型，如 `MaleClothesShop` 类只能实例化 `MaleShirt` 、`MaleCoat` 、`MaleJeans` 这三种与男士相关的服装类对象，并且将相关的实例化代码进行了封装——工厂方法（ Factory Method ），即代码中的 `createClothes` 方法。

如果未来商店再增加新的商店类型，如老年服装商店，我们可以不用对现有的代码进行修改，只要新增相关类即可，保证了“开-闭原则”——”对扩展开放，对修改关闭“。

在设计工厂方法时，不一定要将其设计为抽象方法，可以根据需要保留一个默认的实例化对象创建。



##### 总结

**工厂方法模式**——定义了一个创建对象的接口，但由子类决定要实例化的类是哪一个。工厂方法让类把实例化推迟到子类。

这里的接口是广义上的接口，包括方法（函数），并不特指语法上的抽象类或接口定义。所谓子类决定的意思是实例化的对象是根据子类的类型得到确定，也就是实例化对象的类型依赖于子类的类型。



### Prototype （原型）——对象创建型模式

**意图**

用原型实例指定创建对象的种类，并且通过拷贝这些原型创建新的对象。

**适用性**

- 当一个系统应该独立于它的产品创建、构成的表示时
- 当要实例化的类是在运行时指定时，例如，通过动态装载
- 为了避免创建一个与产品类层次平行的工厂类层次时
- 当一个类的实例只能有几个不同状态组合中的一种时。建立相应数目的原型并克隆它们可能比每次用合适的状态手工实例化该类更方便一些

**参与者**

- Prototype ：声明一个克隆自身的接口
- ConcretePrototye ：实现一个克隆自身的操作
- Client ：让一个原型克隆自身从而创建一个新的对象



### Singleton （单例）——对象创建型模式

**意图**

保证一个类仅有一个实例，并提供一个访问它的全局访问点

**适用性**

- 当类只能有一个实例而且客户可以从一个众所周知的访问点访问它时
- 当这个唯一实例应该是通过子类化可扩展的，并且客户应该无须更改代码就能使用一个扩展的实例时

**参与者**

- Singleton ：定义一个 Instance 操作，允许客户访问它的唯一实例。（ Instance 是一个类操作）；可能负责创建它自己的唯一实例。



#### 例子

单例模式相对比较简单，它让类只有一个自己的实例，其他类访问该实例通过一个访问点（方法），所以只要能够确保类只被实例化一次，并持有该实例化对象就是单例模式。

单例模式实现的基本思路：

1. 将类的构造函数设置为私有（ private ）——外部类无法直接调用构造函数实例化对象；
2. 类有一个自己类型的对象属性，并且是类“自己”拥有的（ static ）——存储类实例化后的单例对象，最好访问限制为私有；
3. 类向外暴露一个方法（访问点/接口，public static ）返回实例化的单例对象——全局访问单例对象的访问点。

但在实际的应用中，因为很多面向对象编程语言支持多线程，如果不对类的实例化过程进行一些互斥或同步限制，那么就可能导致类被多次实例化，所以在考虑多线程的情况下要根据编程语言进行具体的单例模式实现。

以 Java 语言为例，可以通过关键字 `synchronized` 、`volatile` 进行同步与禁止指令重排序保证线程安全；也可以利用 JVM 的类加载机制保证类只被实例化一次。



##### “懒汉式”——线程不安全

```java
public class Singleton {

    private static Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
```

分析：这是最简单的单例模式实现方式，它只有当 `getInstance()` 方法第一次被调用的时候，也即单例对象没有被实例化时才会使用构造函数实例化对象，后续再调用 `getInstance()` 方法则直接返回已有的单例对象。所谓“懒汉”是指对象的实例化是在需要对象的时候才发生。

缺点：没有互斥或同步限制，当多线程执行 `getInstance()` 方法时，可能让 `instance = new Singleton();` 被多个线程执行从而实例化多个对象。

```
(单例对象 instance 没有被实例化，线程一和二同时调用 getInstance() 方法)：
线程一：instance == null -> instance = new Singleton() -> instance = object1
线程二：instance == null -> instance = new Singleton() -> instance = object2
```



##### “懒汉式”——线程安全

将线程不安全的“懒汉式”改为线程安全的方式——将 `getInstance()` 方法进行同步限制（ `synchronized` ），确保在多线程的环境中时刻只有一个线程能够进入并执行该方法。

```java
public class Singleton {

    private static Singleton instance;

    private Singleton() {
    }

    public static synchronized Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
```

分析：通过给 `getInstance()` 方法添加同步限制，保证了多线程环境下的线程安全。

缺点：给方法加锁，导致每次调用方法都要加锁，性能开销大，不合适用在对资源敏感的系统中。



##### “饿汉式”——天然线程安全

对于 Java语言而言，如果在 JVM 加载类的阶段就完成类对象的实例化过程，那么程序在执行时已然有了单例对象，就不会存在多线程同时执行构造函数的情况，保证了线程安全。

```java
public class Singleton {

    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {
    }

    public static Singleton getInstance() {
        return INSTANCE;
    }
}
```

分析：上面的代码中单例对象在类加载阶段就会实例化，并且使用 `final` 关键字让对象“不可变”，也保证了单例对象不能再被实例化，天然的线程安全。

缺点：对象在程序正式运行前就被实例化，即使不使用也会创建对象——这也是“饿汉”的含义，可能浪费内存。



##### 经典实现方法——双重检查锁（Double-Checked Locking，DCL）

结合上面已经实现的三种方式，我们希望一个好的单例模式应该保证线程安全且性能影响小或可以接受。

线程安全要求对实例化部分的代码应该进行同步操作；性能影响小要求应该在首次需要对象的时候才实例化，并且互斥或同步锁的开销小或粒度小。

```java
public class Singleton {
    private static volatile Singleton instance;

    private Singleton() {
    }

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

分析：这次没有在方法声明（定义）上使用 `synchronized` 关键字，让多个线程可以同时进入方法执行，加锁的资源是 Singleton 这个类及后面的实例化过程，锁的开销相对之前降低。而且在单例对象上使用了 `volatile` 关键字修饰禁止 JVM 对该对象相关的操作进行指令重排序，避免其他线程可能拿到一个未初始化完成的对象，进一步保证线程安全。而且上面的实现是“懒加载”方式——首次需要对象时才被实例化。



##### 静态内部类——内部类加载机制的利用

如果不想使用 `synchronized` 关键字，又要达到线程安全与懒加载的效果，可以利用内部类的加载机制。

```java
public class Singleton {

    private Singleton() {
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
}
```

类的加载过程：

```
Singleton 类加载 -> Holder 不加载 -> 调用 getInstance() -> Holder 加载 -> 创建 INSTANCE
```

分析：这种方式中 JVM 保证类加载是线程安全，单例对象只实例化一次。但是持有单例对象的类是单例类的内部类，而不是单例类。同时它是懒加载，没有使用 `synchronized` 关键字，性能好。



##### 枚举单例

利用 Java 语言中枚举类型的特性： JVM 保证枚举类型只有一个实例。

```java
public enum Singleton {

    INSTANCE;

    public void doSomething() {
        System.out.println("this is a singleton by Enum !");
    }
    
    public static void main(String[] args) {
        Singleton.INSTANCE.doSomething();
    }
}
```

从上面的代码中可以看到对单例对象的使用直接通过枚举对象（ `Singleton.INSTANCE` ）完成，它在类加载阶段完成实例化，所以不是延迟加载的方式并保证了线程安全性。除此它还可以防止反射攻击、序列化攻击。



##### 总结

**单例模式**——确保一个类只有一个实例，并提供全局访问点。适用于某个类只有一个实例的情况。

虽然单例模式比较简单，只涉及一个类，但如果考虑到多线程安全、性能、特定编程语言时，它在具体实现上就比较困难，往往需要结合编程语言特性来进行模式的设计与实现。



## 结构型设计模式

结构型模式涉及如何组合类和对象以获得更大的结构。

- 结构型类模式采用继承机制来组合接口或实现。
- 结构型对象模式不是对接口和实现进行组合，而是描述了如何对一些对象进行组合，从而实现新功能的一些方法。因为可以在运行时改变对象组合关系，所以对象组合方式具有更大的灵活性，而这种机制用静态类组合是不可能实现的。



### Adapter （适配器）——类对象结构模式

**意图**

将一个类的接口转换成客户希望的另外一个接口。 Adapter 模式使得原本由于接口不兼容而不能一起工作的那些类可以一起工作。

**适用性**

- 你想使用一个已经存在的类，而它的接口不符合你的需求
- 你想创建一个可以复用的类，该类可以与其他不相关的类或不可预见的类（即那些接口可能不一定兼容的类）协同工作
- （仅适用于对象 Adapter ）你想使用一些已经存在的子类，但是不可能对每一个都进行子类化以匹配它们的接口。对象适配器可以适配它的父类接口。

**参与者**

- Target ：定义 Client 使用的与特定领域相关的接口
- Client ：与符合 Target 接口的对象协同
- Adaptee ：定义一个已经存在的接口，这个接口需要适配
- Adapter ：对 Adaptee 的接口与 Target接口进行适配



#### 例子

##### 背景

当前智能手机取消了单独耳机孔（3.5 mm 音频接口）的设计，音频接口与电源接口（ Type-C 接口）共用，且购买时不再提供有线耳机。假设现在有一部智能手机和一个3.5 mm 的有线耳机，请设计一个适配器实现：将 3.5 mm 音频接口的耳机线“变成”手机可插入的 Type-C 接口耳机，即对于手机来说它感知到的是一个 Type-C 接口类型的耳机。



##### 利用适配器进行转换

分析：由上面的背景和对现实世界进行抽象，手机对外提供的是一个插入接口，并且插入对象的类型必须为 Type-C 类型，3.5 mm 音频耳机需要连接适配器，由适配器将3.5 mm 音频接口“变成” Type-C 类型的接口插入手机使用。我们可以将 Type-C 类型的插线设计为一个接口，需要有线接入手机的设备都要有该类型的插线。适配器则实现了 Type-C 接口的相关功能，并将具体的实现委托给被适配的对象，如3.5 mm 音频接口耳机。

Type-C 类型插线接口：

```java
public interface TypeCWire {
    void insert();
}
```

3.5 mm 音频接口耳机线类：

```java
public class OldHeadset {
    private String type;
    private int volume;

    public OldHeadset() {
        this.type = "3.5mm 耳机线";
        this.volume = 3;
    }

    public void insert() {
        System.out.println(this);
    }

    @Override
    public String toString() {
        return "耳机类型：" + type + "\t音量：" + volume;
    }
}
```

Type-C 接口耳机适配器类：

```java
public class TypeCHeadsetAdapter implements TypeCWire {

    private OldHeadset headset;

    public TypeCHeadsetAdapter(OldHeadset headset) {
        this.headset = headset;
    }

    @Override
    public void insert() {
        headset.insert();
    }
}
```

电源充电线类：

```java
public class ChargerWire implements TypeCWire {

    double power;
    private String type;

    public ChargerWire() {
        this.type = "100w 充电器";
        this.power = 100.0;
    }

    @Override
    public void insert() {
        System.out.println(this);
    }

    @Override
    public String toString() {
        return "充电器：" + type + "\t功率：" + power;
    }
}
```

手机类：

```java
public class Phone {

    public void insert(TypeCWire wire) {
        wire.insert();
    }

    public static void main(String[] args) {
        Phone phone = new Phone();

        OldHeadset headset = new OldHeadset();
        TypeCHeadsetAdapter adapter = new TypeCHeadsetAdapter(headset);
        ChargerWire charger = new ChargerWire();

        phone.insert(adapter);
        phone.insert(charger);
    }
}
```

手机类的 `insert()`方法只接受 `TypeCWire` 接口类型的对象，模拟了手机只有一个 Type-C 接口用于有线连接。在上面的代码中额外增加了一个类 `ChargerWire` 代表手机充电线，它实现了 `TypeCWire` 接口。

在测试中模拟手机依次插入耳机、充电线的行为，其中耳机的插入是通过一个适配器 `TypeCHeadsetAdapter` 类型对象完成的，它将耳机的3.5 mm 音频接口以 Type-C 接口的形式转换给手机，从而实现对旧有耳机的使用。

上面的代码中，充电线的插入是直接调用的自己的方法，而适配器是调用具体耳机的方法，所以适配器只是将手机与耳机之间的接口进行了转换，使得耳机的 3.5 mm 音频接口可以与手机的 Type-C 接口正常工作，耳机与手机之间进行了解耦。

以上代码的实现体现了面向对象设计中的“面向接口编程，而不是实现编程”（ `TypeCWire` 接口的设计）、“多用组合，少用继承”（ `TypeCHeadsetAdapter` 中对 `OldHeadset` 对象的引用）等设计思想。



##### 总结

**适配器模式**：将一个类的接口转换成客户期望的另一个接口。适配器让原本接口不兼容的类可以合作无间。

如例子中手机（客户）的期望接口是 Type-C 类型的插线（目标接口），3.5 mm 音频接口的耳机（原有接口）并不兼容现有的手机接口，所以需要适配器对其进行转换。

上面讲述的主要是“对象”适配器，还有一种类型是“类”适配器，后者通过“多继承”实现——适配器同时继承目标类与被适配类。由于 Java 不支持多继承，所以不展开介绍。



### Bridge （桥接）——对象结构模式

**意图**

将抽象部分与它的实现部分分离，使它们可以独立地变化。

**适用性**

- 你不希望在抽象和它的实现部分之间在一个固定的绑定关系
- 类的抽象以及它的实现都应该可以通过生成子类的方法加以扩充
- 对一个抽象的实现部分的修改应对客户不产生影响，即客户的代码不必重新编译
- 你想在多个对象间共享实现（可能使用引用计数），但同时要求客户并不知道这一点

**参与者**

- Abstraction ：定义抽象类的接口；维护一个指向 Implementor 类型的指针
- RefinedAbstraction ：扩充由 Abstraction 定义的接口
- Implementor ：定义实现类的接口，该接口不一定要与 Abstraction 的接口完全一致，事实上两个接口可以完全不同。一般来讲， Implementor 接口仅提供基本操作，而 Abstraction 则定义了基于这些基本操作的较高层次的操作
- ConcreteImplementor ：实现 Implementor 接口并定义它的具体实现



### Composite （组合）——对象结构型模式

**意图**

将对象组合成树形结构以表示“部分-整体”的层次结构。 Composite 使得用户对单个对象和组合对象的使用具有一致性。

**适用性**

- 你想表示对象的部分-整体层次结构
- 你希望用户忽略组合对象与单个对象的不同，用户将统一地使用组合结构中的所有对象

**参与者**

- Component ：为组合中的对象声明接口；在适当的情况下，实现所有类共有接口的缺省行为；声明一个接口用于访问和管理 Component 的子组件；在递归结构中定义一个接口，用于访问一个父部件，并在合适的情况下实现它
- Leaf ：在组合中表示叶结点对象，叶结点没有子结点；在组合中定义图元对象的行为
- Composite ：定义有子部件的那些部件的行为；存储子部件；在 Component 接口中实现与子部件有关的操作
- Client ：通过 Component 接口操纵组合部件的对象



#### 例子

##### 背景

某软件配置由具体的不同配置项组成，每个配置项包含配置名称和配置值。一般为了便于对软件进行配置，会将配置项按照不同的功能场景进行分类组合，以此形成包含许多配置项的配置组。有时配置过于繁多、功能场景复杂时，会把一些配置组和配置项再进行分类组合，也即软件配置由配置项和配置组共同组成，配置组又包含配置项或配置组。

假设现在的软件配置如下：

```
--窗口大小
--软件语言
--字体
  --字体大小
  --字体颜色
  --字体类型
--显示
  --图片
    --图片格式
    --图片滤镜
  --视频
    --分辨率
    --倍速
  --硬件解码开关
```

请设计实现该软件配置，可以根据需要显示所有的配置或特定名称的配置。

需要定义一个基本的配置类用作配置项的基本表示，同时定义一个配置组类用于表示配置的组合。

```java
public class ConfigItem {

    private String configName;
    private int configValue;

    public ConfigItem(String name, int value) {
        this.configName = name;
        this.configValue = value;
    }

    public void setValue(int value) {
        this.configValue = value;
    }

    public String getConfigName() {
        return configName;
    }

    public void printConfig() {
        System.out.println("配置项名称：" + configName +
                "\t，配置值：" + configValue);

}
```

配置组类：

```java
public class ConfigGroup {

    private String configName;

    private ArrayList<ConfigItem> items;
    private ArrayList<ConfigGroup> groups;

    public ConfigGroup(String configName) {
        this.configName = configName;
        items = new ArrayList<>();
        groups = new ArrayList<>();
    }

    public ConfigGroup(String configName, ArrayList<ConfigItem> items,
                       ArrayList<ConfigGroup> groups) {
        this.configName = configName;
        this.items = items;
        this.groups = groups;
    }

    public String getConfigName() {
        return configName;
    }

    public void addItems(ConfigItem item) {
        items.add(item);
    }

    public void addGroups(ConfigGroup group) {
        groups.add(group);
    }

    public void setItem(String name, int vale) {
        for (ConfigItem item : items) {
            if (item.getConfigName().equals(name)) {
                item.setValue(vale);
                return;
            }
        }
        for (ConfigGroup group : groups) {
            group.setItem(name, vale);
        }
    }

    public void printConfig() {
        System.out.println("----配置组：" + configName + "----");
        if (!items.isEmpty()) {
            System.out.println("****配置子项****");
            for (ConfigItem item : items) {
                item.printConfig();
            }
        }
        if (!groups.isEmpty()) {
            System.out.println("^^^^配置子组^^^^");
            for (ConfigGroup group : groups) {
                group.printConfig();
            }
        }
    }
}
```

##### 面向接口编程

为了能够统一对配置的操作，我们需要提供一个接口，能够满足对配置的一些处理：添加配置、修改配置、打印配置等，外部对配置的使用都使用该接口。

配置接口：

```java
public interface Config {

    void addConfig(Config config);

    boolean setConfigValue(String configName, int configValue);

    void printConfig();

    void printConfigByName(String configName);
}
```

配置项类：

```java
public class ConfigItem implements Config {

    private String configName;
    private int configValue;

    public ConfigItem(String name, int value) {
        this.configName = name;
        this.configValue = value;
    }

    public void setValue(int value) {
        this.configValue = value;
    }

    public String getConfigName() {
        return configName;
    }

    @Override
    public void addConfig(Config config) {
        throw new UnsupportedOperationException("配置项不支持再添加配置！");
    }

    @Override
    public boolean setConfigValue(String configName, int configValue) {
        if (this.configName.equals(configName)) {
            setValue(configValue);
            return true;
        }
        return false;
    }

    @Override
    public void printConfig() {
        System.out.println("配置项名称：" + configName +
                "\t，配置值：" + configValue);
    }

    @Override
    public void printConfigByName(String configName) {
        if (this.configName.equals(configName)) {
            printConfig();
        }
    }
}
```

配置组类：

```java
public class ConfigGroup implements Config {

    private String configName;

    private ArrayList<Config> configs;

    public ConfigGroup(String configName) {
        this.configName = configName;
        configs = new ArrayList<>();
    }

    public ConfigGroup(String configName, ArrayList<Config> configs) {
        this.configName = configName;
        this.configs = configs;
    }

    public String getConfigName() {
        return configName;
    }

    @Override
    public void addConfig(Config config) {
        configs.add(config);
    }

    @Override
    public boolean setConfigValue(String configName, int configValue) {
        for (Config config : configs) {
            if (config.setConfigValue(configName, configValue)) {
                return true;
            }
        }
        return false;
    }

    @Override
    public void printConfig() {
        System.out.println("****^^配置组：" + configName + "^^****");
        for (Config config : configs) {
            config.printConfig();
        }
    }

    @Override
    public void printConfigByName(String configName) {
        if (this.configName.equals(configName)) {
            printConfig();
            return;
        }
        for (Config config : configs) {
            config.printConfigByName(configName);
        }
    }
}
```

分析：上述代码中的重点有两个部分：配置接口定义的方法与组合对象配置组类中方法的实现。前者明确 `Config` 类型的对象应该完成什么操作，提供了一种统一操纵单个对象与组合对象的方式，避免在使用中过于依赖具体的实现。后者通过利用多态（主要是运行时多态）性质，使得我们可以简化对单个对象和组合对象的判断——直接使用 `Config` 对象统一的方法，由程序在运行时决定执行的是单个对象的实现还是组合对象的实现。

通过上面的例子不难发现组合对象形成了一种树形结构的对象集合，我们对对象的操作最终需要由单个对象（叶子结点）承担，如果不利用接口与多态，那么就要在处理组合对象时考虑当前对象是单个对象（叶子结点）还是组合对象（非叶结点）。

还要注意一点的是接口中定义的方法对单个对象或者组合对象不全是有意义的。比如上面例子中 `Config` 接口定义一个 `addConfig(Config config)` 方法，它对于配置项对象是没有意义的，因为配置项就已经是是基本的配置了，不能再添加配置，所以我们可以考虑通过以下方式解决：

1. 在接口中定义一个默认的处理方法；
2. 如果需要返回值，则返回一些无意义、无作用、无影响的值，甚至可以是“空对象”；
3. 正常来说这些方法不应该被不支持的对象执行，所以可以考虑抛出异常，如 `java.lang.UnsupportedOperationException` 异常。

结合组合模式的参与者，上面代码中的 `Config` 接口相当于 `Component ` ， `ConfigItem` 类相当于 `Leaf ` ， `ConfigGroup` 相当于 `Composite ` ，`SoftwareConfig` 相当于 `Client` 。



##### 总结

**组合模式**——允许你将对象组成树形结构来表现“整体/部分”的层次结构。组合能让客户以一致的方式处理个别对象和对象组合。

组合模式提供一个结构，可同时包容个别对象和组合对象。组合模式允许客户对个别对象以及组合对象一视同仁。

组合结构内的任意对象称为组件，组件可以是组合，也可以是叶结点。



### Decorator （装饰器）——对象结构型模式

**意图**

动态地给一个对象添加一些额外的职责。就增加功能来说， Decorator 模式相比生成子类更为灵活。

**适用性**

- 在不影响其他对象的情况下，以动态、透明的方式给单个对象添加职责
- 处理那些可以撤销的职责
- 当不能采用生成子类的方法进行扩充时，一种情况是，可能在大量独立的扩展，为支持每一种组合将产生大量的子类，使得子类数目呈爆炸性增长。另一种情况可能是，类定义被隐藏，或类定义不能用于生成子类

**参与者**

- Component ：定义一个对象接口，可以给这些对象动态地添加职责
- ConcreteComponent ：定义一个对象，可以给这个对象添加一些职责
- Decorator ：维持一个指向 Component 对象的指针，并定义一个与 Component 接口一致的接口
- ConcreteDecorator ：向组件添加职责



#### 例子——小吃下单

##### 背景

某家面馆正在设计顾客点单时的食物的种类：一份基础面食+若干份配料，如一碗牛肉面，再加一个鸡蛋、一块豆腐，价格为16+2+1.5=19.5元。由社会经验可知面馆不一定只买面食，也可能买其他的食物，配料的种类也有许多种。现在需要为每一种具体的搭配设计出具体的类，类具备两种信息：食物的描述、食物的价格。



##### 枚举法

思路：

1. 为每一种可能的食物搭配编写一个具体的类。

缺点：显然这种方法非常粗暴，会让编写代码的人疯掉，产生的类的数量非常多，程序不易维护，代码几乎没有重用性。



##### 利用抽象与组合

分析：在需求中导致搭配复杂的主要原因是配料是否加、配料加几种，而配料是加到某个主食中的。同时从较高的抽象来看，主食与配料都属于食物。在点单时，一般先点主食，再加配料，可以将配料看作是对主食的“装饰”。

思路：

1. 定义一个抽象食物类，它是所有主食与配料的基类。
2. 定义具体的主食类。
3. 定义一个抽象的配料类，它是抽象食物类的子类，是具体配料类的基类。
4. 定义具体的配料类，它包含一个对食物类对象的引用（通过它进行组合）。
5. 每当要再加一个配料时，就将已有食物对象作为该配料对象的属性进行组合。

抽象食物类 Food ：

```java
public abstract class Food {
    String description;
    double price;

    public abstract String getDescription();

    public abstract double cost();
}
```

```java

        Food bfn = new BeefNoodles(16);
        bfn = new Egg(2.0, bfn);
        System.out.println(bfn.getDescription() + "\t价格：" + bfn.cost());

        Food pkn = new PorkNoodles(12);
        pkn = new Tofu(1.5, pkn);
```

在上面的代码中，我们可以看出最终食物的类型是添加的最后一个配料的类型，最初的食物对象在一次次的添加配料（对象构造）中完成“搭配”（装饰）。

仔细阅读代码，会发现抽象配料类 `SideDish` 中我们没有定义任何变量与方法，与它的父类 `Food` 在内部构造上没有区别，那我们可不可以不定义该抽象类，直接使具体的配料类继承自 `Food` 类呢？

答案是：目前来说可以，应该这已经满足了我们例子开始的需求，但认真思考就会发现 `SideDish` 这个抽象类的存在非常有必要。首先，我们之所以要区分主食与配料，不仅是因为语义的原因，更是因为配料其实是在“装饰”主食，让主食有另外的“样子”，定义一个抽象的配料类可以更好地规范具体配料类的实现；其次，如果我们需要配料有区别于主食的行为，那么就可以在抽象类中定义一个方法来实现。

综上，装饰模式的关键在于以下几点：

1. 装饰者与组件（被装饰者）具有相同的基类；
2. 装饰者具有一个指向组件（被装饰者）的引用对象属性；
3. 组件对象被装饰时通过生成一个新的装饰者对象完成装饰；
4. 可以在装饰者中定义新的方法与属性，从而使被装饰对象（组件）具有新的职责（行为、状态），却不用修改被装饰者（组件）的代码。



##### 总结

装饰者模式动态地将责任附加到对象上。若要扩展功能，装饰者提供了比继承更有弹性的替代方案。

在 Java 的 I/O 库中就有大量这样的使用。

装饰者模式可以与其他的生成类设计模式（工厂模式、生成器模式）结合，让被装饰者（组件）实例化时更“优雅”。



### Facade （外观）——对象结构模式

**意图**

为子系统中的一组接口提供一个一致的界面， Facade 模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。

**适用性**

- 当你要为一个复杂子系统提供一个简单接口时。子系统往往因为不断演化而变得越来越复杂，大多数模式使用时都会产生更多更小的类。这使得子系统更具有可复用性，也更容易对子系统进行定制，但也给那些不需要定制子系统的用户带来一些使用上的困难。 Facade 可以提供一个简单的缺省视图，这一视图对大多数用户来说已经足够，而那些需要更多的可定制性的用户可以越过 Facade 层。
- 客户程序与抽象类的实现部分之间存在着很大的依赖性。引入 Facade 将这个子系统与客户以及其他的子系统分离，可以提高子系统的独立性和可移植性。
- 当你需要构建一个层次结构的子系统时，使用 Facade 模式定义子系统中每层的入口点。如果子系统之间是相互依赖的，可以让它们仅通过 Facade 进行通信，从而简化了它们之间的依赖关系

**参与者**

- Facade ：知道哪些子系统类负责处理请求；将客户的请求代理给适当的子系统对象
- Subsystemclasses ：实现子系统的功能；处理由 Facade 对象指派的任务；没有 Facade 的任何相关信息，即没有指向 Facade 的指针

##### 使用统一接口

因为家居智能化，很多家电可以联网进行控制，所以现在需要设计一个统一的接口，通过该接口就能完成之前的多步操作，也即需要一个家电控制中心。

分析：其实我们需要做就是将人和对家电的控制进行解耦，使人不再逐个地对家电进行控制，而是通过一个外在的系统去对家电做统一控制。该外在（外观）系统是所有家电的顶层，各个家电可以视为系统的子系统，人对多个家电的操作可以通过外在（外观）系统提供的一个接口实现。

思路：

1. 新定义一个外观系统——家电控制中心，该系统有所有的家电对象，向外提供一个接口实现对多个家电对象的控制；
2. 修改人对家电的控制操作。

家电控制中心类：

##### 总结

**外观模式**：提供了一个统一的接口，用来访问子系统中的一群接口。外观定义了一个高层接口，让子系统更容易使用。

外观模式设计时考虑了“最少知识”原则，让使用者只与“直接朋友”通信。外观将客户从一个复杂的子系统中解耦。

当需要简化并统一一个很大的接口或者一群复杂的接口时，使用外观。实现一个外观，需要将子系统组合进外观中，然后将工作委托给子系统执行。可以为子系统实现一个以上的外观。



### Flyweight （享元）——对象结构型模式

**意图**

运用共享技术有效地支持大量细粒度的对象。

**适用性**

- 一个应用程序使用了大量的对象
- 完全由于使用大量的对象造成很大的存储开销
- 对象的大多数状态都可变为外部状态
- 如果删除对象的外部状态，那么可能用相对较少的共享对象取代很多组对象
- 应用程序不依赖于对象标识。由于 Flyweight 对象可以被共享，因此对于概念上明显有别的对象，标识测试将返回对象

**参与者**

- Flyweight ：描述一个接口，通过这个接口 Flyweight 可以接受并作用于外部状态
- ConcreteFlyweight ：实现 Flyweight 接口，并为内部状态（如果有的话）增加存储空间。 ConcreteFlyweight 对象必须是可共享的。它所存储的状态必须是内部的，即它必须独立于 ConcreteFlyweight 对象的场景
- UnsharedConcreteFlyweight ：并非所有的 Flyweight 子类都需要被共享。 Flyweight 接口使共享成为可能，但它并不强制共享。在 Flyweight 对象结构的某些层次， UnsharedConcreteFlyweight 对象通常将 ConcreteFlyweight 对象作为子结点。
- FlyweightFactory ：创建并管理 Flyweight 对象；确保合理地共享 Flyweight 。当用户请求一个 Flyweight 时， Flyweight 对象提供一个已创建的实例或者创建一个（如果不存在的话）。
- Client ：维持一个对 Flyweight 的引用；计算或存储一个（或多个） Flyweight 的外部状态



### Proxy （代理）——对象结构型模式

**意图**

为其他对象提供一种代理以控制对这个对象的访问。

**适用性**

- 远程代理：为一个对象在不同的地址空间提供局部代表
- 虚代理：根据需要创建开销很大的对象
- 保护代理：控制对原始对象的访问。保护代理用于对象应该有不同的访问权限的时候
- 智能指引：取代了简单的指针，它在访问对象时执行一些附加操作。典型用途包括：
  - 当第一次引用一个持久对象时，将它装入内存
  - 在访问一个实际对象前，检查是否已经锁定了它，以确保其他对象不能改变它

**参与者**

- Proxy ：保存一个引用使得代理可以访问实体；提供一个与 Subject 的接口相同的接口，这样代理就可以替代实体；控制对实体的存取，并可能负责创建和删除它。
- Subject ：定义 RealSubject 和 Proxy 的共用接口，这样就在任何使用 RealSubject 的地方都可以使用 Proxy
- RealSubject ：定义 Proxy 所代表的实体



#### 例子

##### 背景

在现实生活中很多商品的线下产销都要依赖当地的经销商，由经销商代理厂商在当地的销售活动，主要包括商品的预订（订单）、商品的出货（提货）。客户对商品公司的“交流”全由经销商负责。



##### 模拟代理

对于客户来说无论是经销商还是商品公司，他只关心对方能否提供商店的预订与出货能力，所以经销商与商品公司应该实现同样的接口。经销商作为代理者，向客户提供业务服务，而业务的最终承担者是商品公司，为此经销商应该能够与商品公司交互（如对象引用、方法调用等）。

销售服务接口：

```java
public interface SaleService {
    int order(int counts);
    
    int provide(int orderId);
}
```

商品公司类：

```java
public class SaleCompany implements SaleService {

    private static int ERROR_CODE = -1;

    private HashMap<Integer, Integer> orders;

    public SaleCompany() {
        orders = new HashMap<>();
    }

    @Override
    public int order(int counts) {
        int orderId = orders.size() + 1;
        orders.put(orderId, counts);
        System.out.println("商品预订成功！订单号：" + orderId
                + "\t预订商品数量：" + counts);
        return orderId;
    }

    @Override
    public int provide(int orderId) {
        int counts = orders.getOrDefault(orderId, ERROR_CODE);
        if (counts != ERROR_CODE) {
            System.out.println("提货信息——订单号：" + orderId
                    + "\t数量：" + counts
                    + "。请提货！！！");
            orders.remove(orderId);
        } else {
            System.out.println("订单号：" + orderId + " 不存在提货信息！！！");
        }
        return counts;
    }
}
```

经销商代理类：

```java
public class SaleProxy implements SaleService {

    private static int ERROR_CODE = -1;

    SaleService company;

    public SaleProxy() {
        company = new SaleCompany();
    }

    @Override
    public int order(int counts) {
        if (counts > 0) {
            return company.order(counts);
        } else {
            System.out.println("订单数量不合理！请重新确认！！！");
            return ERROR_CODE;
        }
    }

    @Override
    public int provide(int orderId) {
        return company.provide(orderId);
    }
}
```

测试类：

```java
public class Customer {

    public static void main(String[] args) {
        SaleService service = new SaleProxy();

        int orderId1 = service.order(100);
        service.provide(orderId1);

        int orderId2 = service.order(-2);
        service.provide(orderId2);
    }
}
```

分析：这是非常简单的代理模式实现，外部客户对真实主体的访问需要通过代理对象。由于代理对象与真实主体实现同一接口，所以对于外部客户来说两者没有区别，真实主体是透明的。

在代理对象中我们可以根据方法参数控制外部客户对真实主体的访问，如上面的 `SaleProxy.order(int counts)` 方法。

为了让真实主体能够实现外部客户的调用，需要让代理对象与真实主体对象之间进行“通信交互”，在上面的例子中使用的是“对象引用”，即通过在代理对象中调用引用对象的方法实现。此外还有包括：进程通信，远程调用协议、网络通信协议等。



##### 总结

**代理模式**——为另一个对象提供一个替身或占位符以访问这个对象。代理模式为另一个对象提供代表，以便控制客户对对象的访问，管理访问的方式有许多种。

远程代理管理客户和远程对象之间的交互；虚拟代理控制访问实例化开销开的对象；保护代理基于调用者控制对对象方法的访问。代理模式有许多变体，例如：缓存代理、同步代理、防火墙代理和写入时复制代理。

代理在结构上类似装饰者，但是目的不同。装饰者模式为对象加上行为，而代理则是控制访问。

Java 内置的代理支持，可以根据需要建立动态代理，并将所有调用分配到所选的处理器（ Handler ）。



## 行为型设计模式

行为型模式涉及算法和对象间职责的分配。行为型模式不仅描述对象或类的模式，还描述它们之间的通信模式。这些模式刻画了在运行时难以跟踪的复杂的控制流。它们将你的注意力从控制流转移到对象间的联系方式上来。

- 类行为型模式使用继承机制在类间分派行为
- 对象行为模式使用对象组合而不是继承



### Chain of Responsibility （职责链）——对象行为型模式

**意图**

使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止。

**适用性**

- 有多个对象可以处理一个请求，哪个对象处理该请求运行时自动确定
- 你想在不明确指定接收者的情况下，向多个对象中的一个提交一个请求
- 可处理一个请求的对象集合应被动态指定

**参与者**

- Handler ：定义一个处理请求的接口；实现后继链
- ConcreteHandler ：处理它所负责的请求；可访问它的后继者；如果可处理该请求，就处理之。否则将该请求转发给它的后继者
- Client ：向链上的具体处理者 ConcreteHandler 对象提交请求



### Command （命令）——对象行为型模式

**意图**

将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化，对请求排队或记录请求日志，以及支持可撤销的操作。

**适用性**

- 抽象出待执行的动作以参数化某对象
- 在不同的时刻指定、排列和执行请求
- 支持取消操作
- 支持修改日志，这样当系统崩溃时，这些修改可以被重新做一遍。
- 用构建在原语操作上的高层操作构造一个系统。这样一种结构在支持事务（ transaction ）的信息系统中很常见

**参与者**

- Command ：声明执行操作的接口
- ConcreteCommand ：将一个接收者对象绑定于一个动作；调用接收者相应的操作，以实现 Execute 
- Client ：创建一个具体命令对象并设定它的接收者
- Invoker ：要求该命令执行这个请求
- Receiver ：知道如何实施与执行一个请求相关的操作。任何类都可能作为一个接收者



#### 例子

##### 背景

某绘图软件可以在画布上绘制出任意多个三角形或矩形或圆形，每次绘制操作时需要指明此次绘制的形状，软件提供对上一次操作的撤销操作。例如：用户新建画布，第一步绘制了一个三角形，第二步绘制了一个圆形，第三步撤销上一次的操作，第四次绘制了一个矩形，此时画布中应该只有一个三角形与一个矩形。随着软件迭代，后续软件可以绘制出更多的形状，并提供组合命令的方式绘图（即一次绘制出多个形状）。



##### 面向实现编程

分析：软件根据用户的指令在画布上绘制出相应的形状，并能撤销上一次绘制操作。可以这样设计：画布负责根据用户的指令调用不同的形状进行绘制，同时记录上一次绘制操作的形状，当撤销时将形状“擦除”即可。

思路：

1. 定义一个抽象形状类，包含两个接口：绘制形状与擦除形状，三角形、矩形、圆形都继承自该类。
2. 定义一个画布类，有两个形状对象：一个是当前用户的指令形状，一个是上一次绘制的形状。用户需要绘制形状时，设置当前形状后，画布调用形状的绘制方法进行绘制。用户撤销时，调用形状的擦除方法进行形状擦除。

```java
public class Canvas {

    private List<String> content;

    protected Shape preShape;
    protected Shape nowShape;

    public Canvas(){
        this.preShape = new NoShape();
        this.nowShape = new NoShape();
        this.content = new ArrayList<>();
    }

    public void setNowShape(Shape shape){
        this.nowShape = shape;
    }

    public void drawShape(){
        this.nowShape.draw();
        this.content.add(this.nowShape.getClass().getName());
        this.preShape = this.nowShape;
    }

    public void undo(){
        this.preShape.erase();
        this.content.remove(this.preShape.getClass().getName());
    }

    @Override
    public String toString() {
        return "Canvas{" +
                "content=" + content +
                '}';
    }

    public static void main(String[] args) {
        Canvas canvas = new Canvas();

        // 1.绘制三角形
        canvas.setNowShape(new Triangle());
        canvas.drawShape();

        // 2.绘制圆形
        canvas.setNowShape(new Circle());
        canvas.drawShape();

        // 3.撤销上一步
        canvas.undo();

        // 4.绘制矩形
        canvas.setNowShape(new Rectangle());
        canvas.drawShape();

        // 5.画布内容
        System.out.println(canvas.toString());
    }
```

上面的代码很好的实现了绘图软件的功能，且当增加新的形状时只需要扩展形状类即可。

考虑一下背景中的提到的“组合命令”：一次绘制多个形状，对于这样的需求应该怎么实现？按照上面代码的方式——新定义一个组合形状类即可，似乎是可行的，但是组合形状其实并没有产生新的形状，它依然是由基本的形状组成，如果为此定义一个类，那么不符合为类的抽象原则。而且再审视一下代码，会发现画布类与形状类有点耦合：画布需要传递一个具体的形状对象才能绘制形状，也就是说画布过于“清楚“形状的绘制过程。

重新思考一下绘图软件的逻辑：画布根据用户的指令（或命令）调用相应的形状进行绘制，画布应该只是传达用户的指令并执行，具体的形状绘制不由画面决定。例如”绘制矩形“这一命令，上面的代码是”画布直接向矩形说绘制形状“，而正确的行为应该是“画布告诉形状绘制矩形”，画布对于具体是谁绘制的矩形并不知道。

所以我们需要在画布和形状之间增加一个抽象——命令，由具体的命令来决定由哪个形状绘制，将画布与形状进行解耦。



##### 解耦——使用命令模式

画布与形状之间的交互通过“命令”完成，以此达到解耦的目的。

思路：

1. 定义一个命令抽象类，提供命令执行与命令撤销的接口；
2. 定义具体的操作命令类，继承自命令抽象类，实现具体的命令操作；
3. 修改画布类与形状之间的交互。

```java
public interface Command {

    void execute();

    void undo();
}
```

```java
        this.preCommand = command;
    }

        Command drawTriangle = new DrawTriangleCMD(new Triangle());
        Command drawCircle = new DrawCircleCMD(new Circle());
        Command drawRectangle = new DrawRectangleCMD(new Rectangle());
```

以上面的代码分析命令模式的结构： `main` 方法相当于客户（ `Client` ），画布类 `Canvas` 相当于调用者（ `Invoker` ），具体的形状类 `Triangle` 、 `Rectangle` 、  `Circle` 相当于接收者（ `Receiver` ）。客户使用调用者执行具体命令，具体命令的实现由接收者负责，达到了调用者与接收者解耦的目标。

我们还可以将一组操作定义为一个命令，实现调用一个命令完成多步操作，如：

```java
public class DrawMutiCMDs implements Command {

    Triangle triangle;
    Circle circle;
    Rectangle rectangle;

    public DrawMutiCMDs(Triangle triangle, Circle circle, Rectangle rectangle) {
        this.triangle = triangle;
        this.circle = circle;
        this.rectangle = rectangle;
    }

    @Override
    public void execute() {
        triangle.draw();
        circle.draw();
        rectangle.draw();
    }

    @Override
    public void undo() {
        rectangle.erase();
        circle.erase();
        triangle.erase();
    }
}
```



##### 总结

**命令模式**——将请求封装成对象，这可以让你使用不同的请求、队列，或者日志请求来参数化其他对象。命令模式也可以支持撤销操作。

命令也可以用来实现日志和事务系统。



### Interpreter （解释器）——类行为型模式

**意图**

给定一个语言，定义它的文法的一种表示，并定义一个解释器，这个解释器使用该表示来解释语言中的句子。

**适用性**

- 当有一个语言需要解释执行，并且你可将该语言中的句子表示为一个抽象语法树时，可使用解释器模式。
- 文法简单
- 效率不是关键问题。最高效的解释器通常不是通过直接解释语法分析树实现的，而是首先将它们转换成另一种形式

**参与者**

- AbstractExpression （抽象表达式）：声明一个抽象的解释操作，这个接口为抽象语法树中所有的结点所共享
- TerminalExpression （终结符表达式）：实现与文法中的终结符相关联的解释操作；一个句子中的每个终结符需要该类的一个实例
- NonterminalExpression （非终结符表达式）：对文法中的每一条规则 R : : = R~1~R~2~...R~n~ 都需要一个 NonterminalExpression 类；为从 R ~1~ 到 R ~n~ 的每个符号都维护一个 AbstractExpression 类型的实例变量；为文法中的非终结符实现解释 （ Interpret ）操作。解释一般要递归地调用表示 R~1~ 到 R~n~ 的那些对象的解释操作
- Context （上下文）：包含解释器之外的一些全局信息
- Client （客户）：构建（或被给定）表示该文法定义的语言中一个特定的句子的抽象语法树。该抽象语法树由 NonterminalExpression 和 TerminalExpression 的实例装配而成；调用解释操作



### Iterator （迭代器）——对象行为型模式

**意图**

提供一种方法顺序访问一个聚合对象中的各个元素，而又不需要暴露该对象的内部表示。

**适用性**

- 访问一个聚合对象的内容而无须暴露它的内部表示
- 支持对聚合对象的多种遍历
- 为遍历不同的聚合结构提供一个统一的接口（即支持多态迭代）

**参与者**

- Iterator （迭代器）：迭代器定义访问和遍历元素的接口
- ConcreteIterator （具体迭代器）：具体迭代器实现迭代器接口；对该聚合遍历时跟踪当前位置
- Aggregate （聚合）：聚合定义创建相应迭代对象的接口
- ConcreteAggregate （具体聚合）：具体聚合实现创建相应迭代器的接口，该操作返回 ConcreteIterator 的一个适当的实例

服装商品列表迭代器类：

```java
public class ClothesIterator implements ListIterator {

    private ArrayList<CommodityInfo> clotheslist;
    private int position;

    public ClothesIterator(ArrayList<CommodityInfo> clotheslist) {
        this.clotheslist = clotheslist;
        this.position = 0;
    }

    @Override
    public boolean hasNext() {
        if (position < clotheslist.size() && clotheslist.get(position) != null) {
            return true;
        }
        return false;
    }

    @Override
    public Object next() {
        CommodityInfo commodityInfo = null;
        if (hasNext()) {
            commodityInfo = clotheslist.get(position);
            position++;
        }
        return commodityInfo;
    }
}
```

### Mediator （中介者）——对象行为型模式

**意图**

用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

**适用性**

- 一组对象以定义良好但复杂的方式进行通信，产生的相互依赖关系结构混乱且难以理解。
- 一个对象引用其他很多对象并且直接与这些对象通信，导致难以复用该对象
- 想定制一个分布在多个类中的行为，而又不想生成太多的子类

**参与者**

- Mediator （中介者）：定义了一个接口用于与各同事对象通信
- ConcreteMediator （具体中介者）：具体中介者通过协调各同事对象实现协作行为；了解并维护它的各个同事
- Colleagueclass （同事类）：每一个同事类都知道它的中介者对象；每一个同事对象在需要与其他同事通信的时候，与它的中介者通信



### Memento （备忘录）——对象行为型模式

**意图**

在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态。这样以后就可将该对象恢复到原先保存的状态

**适用性**

- 必须保存一个对象在某个时刻的（部分）状态，这样以后需要时它才能恢复到先前的状态
- 如果一个接口让其他对象直接得到这些状态，将会暴露对象的实现细节并破坏对象的封装性

**参与者**

- Memento ：备忘录存储原发器对象的内部状态。原发器根据需要决定备忘录存储原发器的哪些内部状态；防止原发器以外的其他对象访问备忘录。
- Originator （原发器）：原发器创建一个备忘录，用以记录当前时刻它的内部状态；使用备忘录恢复内部状态
- Caretaker （管理者）：负责保存好备忘录；不能对备忘录的内容进行操作或检查



### Observer （观察者）——对象行为型模式

**意图**

定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。

**适用性**

- 一个抽象模型有两个方面，其中一个方面依赖于另一方面。将这二者封装在独立的对象中，以使它们可以各自独立地改变和复用
- 对一个对象的改变需要同时改变其他对象，而不知道具体有多少对象有待改变
- 一个对象必须通知其他对象，而它又不能假定其他对象是谁。换言之，你不希望这些对象是紧密耦合的

**参与者**

- Subject （目标）：目标知道它的观察者。可以有任意多个观察者观察同一个目标；提供注册和删除观察者对象的接口
- Observer （观察者）：为哪些在目标发生改变时需要获得通知的对象定义一个更新接口
- ConcreteSubject ：将有关状态存入各 ConcreteObserver 对象；当它的状态发生改变时，向其各个观察者发出通知
- ConcreteObserver （具体观察者）：维护一个指向 ConcreteSubject 对象的引用；存储有关状态，这些状态应与目标的状态保持一致；实现 Observer 的更新接口，以使自身状态与目标的状态保持一致



#### 例子——商品供应量

##### 背景

某公司的生产部门在生产每一批次的产品时，都会公布本批次产品的生产总数与残次品数（单位：件），目前有其他两个部门会使用这些信息：一个部门A计算该批次产品的合格率，一个部门B计算该批产品的预计销售总额（单位：元，计算公式：合格品数 × 销售单价）。要求：当生产部门更新生产数据时，需要该数据信息的部门可以及时得到新数据并进行计算，后续可能有新的部门会要求生产部门提供数据，也可能现有部门不再需要该数据。



##### 直接（简单）实现

思路：

1. 定义产品类，该类提供产品的生产总数与残次品数，当更新生产数据时可以发布订阅通知更新订阅者的状态。
2. 定义多个部门类，部门类可以订阅产品类的数据，并提供一个更新接口让产品类可以通知部门类进行状态更新。

产品类：

```java
public class Product {
    DepartmentA dpA;
    DepartmentB dpB;

    int total;
    int defectCount;

    public Product(int total, int defectCount) {
        this.total = total;
        this.defectCount = defectCount;
    }

    public void addDPA(DepartmentA dpA){
        this.dpA = dpA;

    public void addDPB(DepartmentB dpB){
        this.dpB = dpB;

        dpA.update();
        dpB.update();

    public void onChanged(){
        notifyDP();
    }

    public void setDate(int total, int defectCount){
        this.total = total;
        this.defectCount = defectCount;
        onChanged();
    }

    public int getTotal() {
        return total;
    }

    public int getDefectCount() {
        return defectCount;
    }
}
```

**存在的问题**：

1. 上面的代码实现中，我们是面向实现编程，而不是面向接口编程，与设计原则不符，不利于代码重用与修改；
2. 当要增加或删除某些部门类时，需要显式的修改 产品类 Product 中的属性，代码修改与扩展繁琐，而且上面的代码没有体现动态新增或删除订阅者（部门类）的逻辑；



##### 面向接口编程&使用容器增/删订阅者

思路：

1. 对于产品类而言，它就是一个消息的发布者，它将消息更新的内容通知它的订阅者，所以产品类在观察者模式中属于的主题 Subject 。它的抽象功能包括以下几个：
   - 提供订阅者（观察者）订阅消息
   - 提供订阅者（观察者）取消订阅
   - 通知订阅者（观察者）更新消息
2. 对于部门类，它是产品类消息的订阅者（观察者），它向产品类（主题）提供一个用于通知更新消息的接口，它属于观察者模式中的观察者 Observer 。它的抽象功能包括：
   - 更新订阅的消息
3. 将上面分析中的功能抽象为两个接口： Subject 和 Observer ，产品类实现 Subject 接口，部门类实现 Observer 接口。
4. 为了动态的增删订阅者，可以在实现 Subject 接口的产品类中使用容器类来动态存储与遍历订阅者对象。

Subject （主题接口）：

```java
public interface Subject {
    void registerObserver(Observer o);

    void deleteObserver(Observer o);

    void notifyObservers();
}
```

观察者 Observer 接口：

```java
public interface Observer {
    void update();
}
```

产品类 Product ：

```java
import java.util.ArrayList;

public class Product implements Subject {

    ArrayList<Observer> observerList;

    int total;
    int defectCount;

    public Product(int total, int defectCount) {
        this.total = total;
        this.defectCount = defectCount;
        observerList = new ArrayList<>();
    }

    @Override
    public void registerObserver(Observer o) {
        observerList.add(o);
    }

    @Override
    public void deleteObserver(Observer o) {
        int index = observerList.indexOf(o);
        if (index != -1) {
            observerList.remove(index);
        }
    }

    @Override
    public void notifyObservers() {
        for (Observer o : observerList) {
            o.update();
        }

    }

    public void onChanged() {
        notifyObservers();
    }

    public void setDate(int total, int defectCount) {
        this.total = total;
        this.defectCount = defectCount;
        onChanged();
    }

    public int getTotal() {
```

##### 使用 JDK 内置的观察者接口

在 JDK 中提供了一些实现观察者模式的类或接口，我们在使用时不用自定义主题 Subject 和观察者 Observer 接口。这里以 `java.util` 包中的 `Observable` 类和 `Observer` 接口为例，前者作为观察者模式中的主题 Subject ，是被观察对象，注意它是类，使用时要继承；后者作为观察者模式中的观察者 Observer ，它是接口，使用时实现接口方法 `void update(Observable o, Object arg);` 。

 `Observable` 类和 `Observer` 接口的源码十分简短，建议可以自行阅读，会发现与我们自定义的接口差不多。

`Observable` 类继承后，我们只需要在数据更新时调用 `setChanged()` 和 `notifyObservers()` 或 `notifyObservers(Object arg)` 方法即可。

`Observer` 接口实现后，重写`update(Observable o, Object arg)` 方法，同样需要在对象创建时向 `Observable` 对象添加观察者，使用 `addObserver(Observer o)` 方法，删除观察者使用 `deleteObserver(Observer o)` 方法。

以 Product 类和 DepartmentA 类为例：

```java
package jdk;

import java.util.Observable;

public class Product extends Observable {
    int total;
    int defectCount;

    public Product(int total, int defectCount) {
        this.total = total;
        this.defectCount = defectCount;
    }

    public void onChanged() {
        setChanged();
        notifyObservers();
    }

    public void setDate(int total, int defectCount) {
        this.total = total;
        this.defectCount = defectCount;
        onChanged();
    }

    public int getTotal() {
        return total;
    }

    public int getDefectCount() {
        return defectCount;
    }
}
```

```java
package jdk;

import java.util.Observable;
import java.util.Observer;

public class DepartmentA implements Observer {
    Product product;

    float passRate;

    public DepartmentA(Product product) {
        this.product = product;
        this.product.addObserver(this);
    }

    @Override
    public void update(Observable o, Object arg) {
        if(o instanceof Product){
            product = (Product) o;
            if (product.getTotal() != 0) {
                passRate = (float) (product.getTotal() - product.getDefectCount()) / product.getTotal();

            }
        }
    }

    public void report() {
        System.out.println("本批产品合格率为：" + passRate + " 。");
    }
}
```

使用 JDK 的观察者可以简化我们的代码，但难免会缺少灵活性与特性，比如在 Java 语言中只允许单继承，而 `java.util.Observable` 是一个类，这会有所限制。所以如果熟练模式的话还是建议自己实现观察者模式比较好，而且从开始的例子可以看出这并不难实现。



##### 总结

**观察者模式**：在对象之间定义一对多的依赖，这样一来，当一个对象改变状态，依赖它的对象都会收到通知，并自动更新。



### State （状态）——对象行为型模式

**意图**

允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。

**适用性**

- 一个对象的行为取决于它的状态，并且它必须在运行时根据状态改变它的行为
- 一个操作中含有庞大的多分支的条件语句，且这些分支依赖于该对象的状态。这个状态通常用一个或多个枚举常量表示。通常，有多个操作包含这一相同的条件结构

**参与者**

- Context （环境）：定义客户感兴趣的接口；维护一个 ConcreteState 子类实例，这个实例定义当前状态
- State ：定义一个接口以封装与 Context 的一个特定状态相关的行为
- ConcreteStateSubclasses （具体状态子类）：每一子类实现一个与 Context 的一个状态相关的行为



#### 例子

##### 背景

一个简化的相机模型，它共有三个状态：开机状态、拍照状态、关机状态，使用者通过两个按钮对它进行控制：电源按钮与拍摄按钮。不同状态下按下按钮的状态转换如下：

- 开机状态：按下电源按钮进入关机状态；按下拍摄按钮进入拍照状态。
- 拍照状态：按下电源按钮进入关机状态；按下拍摄按钮拍摄照片。
- 关机状态：按下电源按钮进入开机状态；按下拍摄按钮无反应（仍处于关机状态）。



##### 直接对状态进行条件判断

相机模型有三个状态（开机、拍照、关机）和两个对外操作（电源按钮、拍摄按钮），使用一个变量记录当前相机的状态，通过条件判断从而决定某个操作下相机的行为。

相机类：

```java
public class Camera {

    public static final int STATE_POWER_OFF = 0;
    public static final int STATE_POWER_ON = 1;
    public static final int STATE_SHOOT = 2;

    private int state = STATE_POWER_OFF;

    public void turnPower() {
        if (state == STATE_POWER_OFF) {
            state = STATE_POWER_ON;
            System.out.println("开机中...");
        } else if (state == STATE_SHOOT) {
            state = STATE_POWER_OFF;
            System.out.println("关机中...");
        } else if (state == STATE_POWER_ON) {
            state = STATE_POWER_OFF;
            System.out.println("关机中...");
        }
    }

    public void turnShoot() {
        if (state == STATE_POWER_OFF) {
            System.out.println("相机已关机，不能拍摄！！！");
        } else if (state == STATE_POWER_ON) {
            state = STATE_SHOOT;
            System.out.println("进入拍照模式中...");
        } else if (state == STATE_SHOOT) {
            System.out.println("拍摄照片中...一个美丽的照片...");
        }
    }

    @Override
    public String toString() {
        return "相机当前状态：" + state;
    }
}
```

分析：由于相机的状态明确，所以用静态常量分别存储相机的状态，多个实例可以共用这些状态常量，每个实例中独自拥有一个状态变量记录当前相机的状态。相机提供两个接口（方法） `turnPower()` 和 `turnShoot()` 模拟按下电源与拍摄按钮，方法实现中需要针对当前相机的状态进行不同的处理，所以这两个方法中有大量的条件判断和不同的逻辑处理。

缺点：当增加状态或某个状态下行为处理要更改时，不得不对相机类中的代码进行修改，且涉及条件判断与相应的分支处理，这违反了“开—闭原则”，不利于修改与维护。



##### 面向接口&&状态行为由具体的状态对象处理

例子中无论什么状态都要处理两类行为——按下电源、拍摄按钮，所以不妨从状态中抽象出一个接口，相机类面向接口编程，这样在相机类提供的两个接口（方法） `turnPower()` 和 `turnShoot()` 中只能察觉到一个状态对象在处理行为。

分析：检查相机类会发现代码中的条件判断消失了，取而代之的是状态对象的方法调用。我们不再需要大量的条件判断以决定如何处理行为，而是运行时具体的对象负责实现，这与策略模式有些类似，但是策略模式的具体对象一般是明确的、有方案的，而状态模式中具体状态对象会随着程序运行发生转换，从这个对象转换成那个对象则取决于外部的操作。

在上面的实现中每个相机实例都有一份自己的状态对象的引用，实例间不共享状态对象，这是因为我们将实例的状态转换交给了状态对象处理（创建状态对象时传入了一个相机对象的引用），因此每个相机实例应该有自己的状态对象。如果我们能够在相机类中完成状态的转换，那么就可以使用共享的状态对象。

##### 总结

**状态模式**——允许对象在内部状态改变时改变它的行为，对象看起来好像修改了它的类。

状态模式允许一个对象基于内部的状态而拥有不同的行为，状态模式用类代表状态。 Context 会将行为委托给当前状态对象。通过将每个状态封装进一个类，我们把以后需要做的任何改变局部化了。

状态转换可以由 State 类或 Context 类控制。状态类可以被多个 Context实例共享。

使用状态模式通常会导致设计中类的数目大量增加，但比起代码的维护与修改这是值得的。



### Strategy （策略）——对象行为型模式

**意图**

定义一系列的算法，把它们一个个封装起来，并且使它们可相互替换。本模式使得算法可独立于使用它的客户而变化。

**适用性**

- 许多相关的类仅仅是行为有异。“策略”提供了一种用多个行为中的一个行为来配置一个类的方法
- 需要使用一个算法的不同变体
- 算法使用客户不应该知道的数据。可使用策略模式以避免暴露复杂的、与算法相关的数据结构
- 一个类定义了多种行为，并且这些行为在这个类的操作中以多个条件语句的形式出现。将相关的条件分支移入它们各自的 Strategy 类中以代替这些条件语句

**参与者**

- Strategy ：定义所有支持的算法的公共接口。 Context 使用这个接口来调用某 ConcreteStrategy 定义的算法
- ConcreteStrategy ：以 Strategy 接口实现某具体算法
- Context ：用一个 ConcreteStrategy 对象来配置；维护一个对 Strategy 对象的引用；可定义一个接口来让 Strategy 访问它的数据



#### 例子——鸭子类设计

> 例子参考：《Head First 设计模式 （中文版）》2007-09，中国电力出版社

**存在的问题**：当添加一个新的鸭子类时，都要重写父类的方法，即便这个方法已经在某个子类中实现了，如新增加一个家鸭类，它和绿头鸭只是外表不一样而已，但其它行为一样；新增加一个木头鸭，它即不会叫、也不会飞，但依旧要重写父类方法。综上，**使用继承并没有实现良好的代码重用**。



##### 实现接口

在上面的代码中，其实已经在实现接口了：父类中定义抽象的方法，每个子类都要实现自己的具体的方法。它存在的问题依旧是当新增加类时，要重写大量的重复代码。



##### 面向接口编程

认真思考可以发现例子中不变的是鸭子这个抽象的概念，变的是具体鸭子的行为：同一行为，不同的鸭子有相同或不同的特征（执行）方式，如大多数鸭子用翅膀飞，少数鸭子不会飞或用其他方式飞。重复的代码就是根据具体的鸭子类型重写已有的方法。

所以可以将要重写的方法视作一个方法（算法）族，在执行时从方法族中选择某个具体的方法。

思路：

1. 将行为（重写的方法）：鸣叫（ quack ）、飞（ fly ）定义为抽象类或接口类，并在父类 Duck 中定义类型为抽象类或接口类的变量，使得把实际的行为执行委托给实现抽象方法或接口的实现子类。
2. 实现鸣叫、飞等方法。
3. 可以通过 Duck 类的构造方法或使用 setter 方法的形式指定实际的变量类型。
4. 通过调用变量方法的形式实现行为。

**策略模式**定义了算法族，分别封装起来，让它们之间可以互相替换，此模式让算法的变化独立于使用算法的客户。



### Template Method （模板方法）——类行为型模式

**意图**

定义一个操作中的算法的骨架，而将一些步骤延迟到子类中。 Template Method 使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤。

**适用性**

- 一次性实现一个算法的不变部分，并将可变的行为留给子类来实现
- 各子类中公共的行为应被提取出来并集中到一个公共父类中以避免代码重复。
- 控制子类扩展。模板方法只在特定点调用钩子操作，这样就只允许在这些点进行扩展

**参与者**

- AbstractClass ：定义抽象的原语操作，具体的子类将重定义它们以实现一个算法的各步骤；实现一个模板方法，定义一个算法的骨架。该模板方法不仅调用原语操作，也调用定义在 AbstractClass 或其他对象中的操作
- ConcreteClass ：实现原语操作以完成算法中与特定子类相关的步骤



#### 例子

##### 背景

粽子的制作步骤可以分为以下几步：1.折叠粽叶成漏斗状；2.填充糯米与馅料；3.用绳子捆绑粽子。由于南北差异，粽子大致分为两类：甜粽（可选馅料有白糖、红枣、豆沙、蜜饯等）与咸粽（可选馅料有咸蛋黄、猪肉等）。据此编写粽子类。



##### 直接编写

按要求编写两个类：甜粽类与咸粽类。

甜粽类：

```java
public class SweetZongZi {

    public void make(){
        fold();
        fill();
        bind();
    }

    public void fold(){
        System.out.println("折叠粽叶...");
    }

    public void fill(){
        System.out.println("填充糯米、白糖、红枣...");
    }

    public void bind(){
        System.out.println("捆绑粽子...");
    }
}
```

咸粽类：

```java
public class SaltyZongZi {

    public void make(){
        fold();
        fill();
        bind();
    }

    public void fold(){
        System.out.println("折叠粽叶...");
    }

    public void fill(){
        System.out.println("填充糯米、咸蛋黄、猪肉...");
    }

    public void bind(){
        System.out.println("捆绑粽子...");
    }
}
```

分析：上面的代码虽然实现了需求，但是不难发现甜粽与咸粽两个类中有大量相同或相似的代码，按照良好的面向对象设计原则，我们应该将其中相同的部分抽离出来。



##### 定义一个模板

甜粽与咸粽的制作流程框架是一致的，因为它们都是粽子，只是馅料不同才导致粽子的类型不同，所以我们可以将粽子的制作过程先定义成一个统一模板，模板中的差异不同部分由具体的粽子负责实现。

思路：

1. 定义一个粽子基类，基类中对所有粽子相同的操作进行实现封装，对于不同的操作则由具体子类负责实现完成。
2. 使甜粽、咸粽都继承自粽子基类，删除冗余的代码。

粽子基类：

```java
public abstract class ZongZi {

    public final void make() {
        fold();
        fill();
        bind();
    }

    public final void fold() {
        System.out.println("折叠粽叶...");
    }

    public abstract void fill();

    public final void bind() {
        System.out.println("捆绑粽子...");
    }
}
```

甜粽类：

```java
public class SweetZongZi extends ZongZi {

    public void fill() {
        System.out.println("填充糯米、白糖、红枣...");
    }
}
```

咸粽类：

```java
public class SaltyZongZi extends ZongZi {

    public void fill() {
        System.out.println("填充糯米、咸蛋黄、猪肉...");
    }
}
```

测试类：

```java
public class Main {
    public static void main(String[] args) {
        SweetZongZi sweetZongZi = new SweetZongZi();
        sweetZongZi.make();

        System.out.println("***********");

        SaltyZongZi saltyZongZi = new SaltyZongZi();
        saltyZongZi.make();
    }
}
```

分析：通过粽子基类将粽子的制作步骤定义为一个统一模板方法，该方法的每一步是一个方法的调用——粽子的制作的某个小步骤，所有粽子的制作按照该模板方法进行，只是部分步骤有所不同，有差异的步骤就由具体的子类进行实现。

通过模板方法可以将多个类共有的算法抽象出来，算法又可以细化为一步步的小操作，将小操作视为其他方法的调用，不同的类在算法的某些步骤上存在实现差异，但算法流程一致，把没有差异的操作（步骤）统一交给基类实现，有差异的操作让具体的子类负责实现。模板方法让我们可以在编写算法的某个具体实现时只考虑差异的部分。

如果现在新增加一种品味的粽子（比如：辣味），那么只需要编写一个粽子类并实现 `fill()` 方法就好。

在上面的代码实现中，我们利于了 Java 的语法特性—— `final` 关键字对没有实现差异的方法（步骤）进行修饰，避免了子类对基类中这些方法的覆盖（重写），保证了算法步骤（框架）对所有子类一样。



##### 为模板添加钩子

假如现在制作粽子完成后需要询问顾客是否包装粽子。

粽子基类：

```java
public abstract class ZongZi {

    public final void make() {
        fold();
        fill();
        bind();
        wrap();
    }

    public final void fold() {
        System.out.println("折叠粽叶...");
    }

    public abstract void fill();

    public final void bind() {
        System.out.println("捆绑粽子...");
    }

    public void wrap(){
        System.out.println("不进行包装...");
    }
}
```

甜粽类：

```java
public class SweetZongZi extends ZongZi {

    public void fill() {
        System.out.println("填充糯米、白糖、红枣...");
    }

    public void wrap(){
        System.out.println("需要包装吗?（Y/N）");
        Scanner scanner = new Scanner(System.in);
        String choice = scanner.nextLine().toLowerCase();
        if(choice.startsWith("y")){
            System.out.println("使用甜粽商品礼盒包装...");
        }else{
            System.out.println("不进行包装...");
        }
        scanner.close();
    }
}
```

测试类：

```java
public class Main {
    public static void main(String[] args) {
        SweetZongZi sweetZongZi = new SweetZongZi();
        sweetZongZi.make();

        System.out.println("***********");

        SaltyZongZi saltyZongZi = new SaltyZongZi();
        saltyZongZi.make();
    }
}
```

运行测试类会发现制作甜粽完成后，会询问是否包装，而制作咸粽不会，因为我们没有编写咸粽对包装的具体实现，咸粽在调用包装函数 `wrap()` 时使用的是基类默认的实现。这就是模板方法提供的“钩子”——让算法可以“额外”做些什么操作。

一般基类会将钩子实现为空方法（无操作）或者提供一些默认的操作，由具体的子类选择要不要覆盖它，增加子类实现算法的个性化需求。



##### 总结

**模板方法**——在一个方法中定义一个算法的骨架，而将一些步骤延迟到子类中。模板方法使得子类可以不改变算法结构的情况下，重新算法中的某些步骤。

模板方法充分地体现了“好莱坞”原则——别调用我们，我们会调用你。算法的执行过程由高层模块决定，低层模块只需要提供自己的功能（方法）即可，至于何时何地被调用则由高层模块（框架）决策。如例子中当我们调用 `make()` 方法时，整个的过程其实是在基类中就被定义好了，子类中没有对流程的任何控制，子类的方法 `fil()` 在 `make()` 中被调用。



### Visitor （访问者）——对象行为型模式

**意图**

表示一个作用于某对象结构中的各元素的操作。它使你可以在不改变各元素的前提下定义作用于这些元素的新操作。

**适用性**

- 一个对象结构包含很多类对象，它们有不同的接口，而你对这些对象实施一些依赖于其具体类的操作
- 需要对一个对象结构中的对象进行很多不同并且不相关的操作，而你想避免让这些操作“污染”这些对象的类
- 定义对象结构的类很少改变，但经常需要在此结构上定义新的操作。改变对象结构类需要重定义对所有访问者的接口，这可能需要很大的代价。如果对象结构类经常改变，那么可能还是在这些类中定义这些操作比较好

**参与者**

- Visitor ：为该对象结构中 ConcreteElement 的每一个类声明一个 Visitor 操作。该操作的名字和特征标识了发送 Visit 请求给该访问者的类。这使得访问者可以确定正被访问元素的具体的类。这样访问者就可以通过该元素的特定接口直接访问它
- ConcreteVisitor ：实现每个由 Visitor 声明的操作。每个操作实现本算法的一部分，而该算法片段是对应于结构中对象的类。 ConcreteVisitor 为该算法提供了上下文并存储它的局部状态。这一状态常常在遍历该结构的过程中累积结果
- Element ：定义一个 Accept 操作，它以一个访问者为参数
- ConcreteElement ：实现 Accept 操作，该操作以一个访问者为参数
- ObjectStructure ：能枚举它的元素；可以提供一个高层的接口以允许访问者访问它的元素；可以是一个组合或是一个集合，如一个列表或一个无序集合



## 复合模式——模式与模式的合作

在一些面向对象的设计中会同时使用到多个设计模式。模式通常被一起使用，并被组合在同一个设计解决方案中。复合模式在一个解决方案中结合两个或多个模式，以**解决一般或重复发生的问题**。

在程序设计时不需要一定使用设计模式，有时候用好的面向对象设计原则就可以解决问题。**采用模式时必须考虑到这么做是否有意义，绝对不能为了使用模式而使用模式**。

过度使用设计模式可能导致代码被过度工程化。应该总是用最简单的解决方案完成工作，并在真正需要模式的地方才使用它。

设计模式常常会产生一些额外的类和对象，所以会增加设计的复杂度。设计模式也会在你的设计中加入更多层，这不但增加复杂性，而且效率下降。

有时使用设计模式会大材小用。许多时候回头看看设计原则，你会发现有简单得多的解决方案能解决相同的问题。
